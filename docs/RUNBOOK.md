## 1. 起動 / 停止 / 再起動

```bash
# 全サービス起動
docker compose up -d

# 状態確認
docker compose ps

# 停止 (コンテナ保持)
docker compose stop

# 停止 + コンテナ削除
docker compose down

# 個別再起動
docker compose restart <service-name>
```

依存起動順が問題になる場合は個別に `up -d` で立ち上げる。特に notification-service は user-management に依存するため先に user-management を起動する。

## 2. ヘルスチェックの確認

各サービスは以下を最低限備える。

| エンドポイント | 用途 |
| :-- | :-- |
| `GET /livez` | プロセスの生存 (外形監視向け・軽量) |
| `GET /healthz` | 依存 (DB / キュー / 上流 API) を含めた活性性 |
| `GET /readyz` | トラフィックを受けられる状態か |

```bash
curl -sf http://localhost:${PORT}/healthz | jq .
make health  # 全サービス横断
```

## 3. ログとメトリクスの入り口

- **ログ**: JSON 行。`docker compose logs -f --tail=200 <service> | jq .`
- **メトリクス**: 各サービスは `/metrics` を Prometheus 形式で公開
- **相関 ID**: `X-Request-Id` ヘッダーを全サービスで透過。障害追跡は影響ユーザーの `request_id` から始める

```bash
# 特定リクエストを横断で追跡
docker compose logs | jq 'select(.request_id == "REQ-...")'
```

## 4. デプロイ

### 事前チェック

1. `main` が CI グリーン
2. マイグレーションが必要な場合、DDL は下位互換を保つ (加える → コード切替 → 削るの二段階を守る)
3. `CHANGELOG.md` にエントリがある

### 手順

```bash
git tag -a v0.X.Y -m "..."
git push origin v0.X.Y
make deploy ENV=<staging|production>
```

### デプロイ後の確認

- 全サービスの `/healthz` が OK
- エラー率 / P95 レイテンシがベースライン内
- 主要ユーザーフロー 1 系統を手動で通す (サインアップ or 通知配信 など)

## 5. ロールバック

原則、直前のグリーンなイメージタグに戻して再デプロイ。

```bash
git tag --sort=-committerdate | head -5
make deploy ENV=production TAG=v0.X.Y-1
```

DB マイグレーションが絡む場合、下位互換が保たれていれば安全にロールバック可能。壊す変更は "前方回復" (追加パッチ) を選ぶ。

## 6. インシデント一次対応

| 深刻度 | 判断基準 | 対応 |
| :-- | :-- | :-- |
| Sev-1 | 全ユーザー影響 or データロス懸念 | 即座にオンコール招集 |
| Sev-2 | 一部ユーザー影響 or 主要機能劣化 | 30 分以内に着手 |
| Sev-3 | 単発エラー・軽微な劣化 | 翌営業日中に対応 |

### 一次対応フロー

1. **止血 (Mitigate)**: ロールバック・機能フラグ OFF・レートリミット引き下げ
2. **観測 (Observe)**: ゴールデンシグナル (レイテンシ / トラフィック / エラー / サチュレーション)
3. **記録 (Log)**: Slack のインシデント専用スレッドに時系列で残す
4. **共有 (Communicate)**: Sev-1 / Sev-2 は 30 分ごとにステークホルダー共有
5. **収束 (Resolve)**: 影響収束を宣言し、ポストモーテムのオーナーを決める

## 7. サービス別 早見表

### user-management

- 主要責務: 認証・認可、ユーザープロファイル
- 停止時の影響: ログイン不能、他サービスの認可判定不能 (Sev-1 相当)
- 一次対応: DB コネクション枯渇の確認 → 認可キャッシュのウォームアップ確認

### analytics-engine

- 主要責務: メトリクス集計・時系列クエリ
- 停止時の影響: ダッシュボード表示不可 (Sev-2 相当・書き込みパスが生きていれば回復可能)
- 一次対応: バックログ深さの確認 → クエリキューの詰まり調査

### notification-service

- 主要責務: メール・プッシュ通知の送出
- 停止時の影響: 通知遅延・欠落 (Sev-2 相当)
- 一次対応: 送信キューの再駆動 → 上流プロバイダのステータス確認 → リトライ設定の確認
